# v2.4 — Secure by default

Design for the v2.4 release listed in [ROADMAP.md](../../ROADMAP.md). Written
2026-08-31, against v2.3.0.

## The problem

The in-cluster tunnel server is unauthenticated and unencrypted. Anything in
the cluster that can reach its Service can open a tunnel to the developer's
machine, and anything that can reach the gRPC port can attach as a client and
be handed the traffic meant for that machine. [docs/security.md](../security.md)
describes this honestly today; this release fixes it.

`--tls` exists but is rejected by `expose` and `inject`, because nothing
mounts a certificate into the server container and `--cert`/`--key` reach it
as a single unparsed argument.

## Decisions

Taken before the design, and the design follows from them:

1. **Both on by default.** A plain `ktunnel expose myapp 8000` is encrypted
   and authenticated with no new flags.
2. **Secret preferred, env fallback.** ktunnel creates a Secret when it can
   and degrades to a token in the pod spec when `secrets: create` is denied,
   rather than refusing to run.
3. **Version skew does not abort.** An older server image yields a plaintext
   tunnel with a printed warning, not a failure.
4. **`inject` is token-only.** No volume patched into a Deployment ktunnel
   does not own.
5. **`--tls` becomes a no-op; `--insecure` is the escape hatch.**

## Credential generation

A new `pkg/creds` package: pure Go, no cluster awareness, nothing written to
disk.

`Generate(name, namespace string) (*Bundle, error)` produces, in memory:

- a self-signed ECDSA P-256 CA
- a server leaf signed by it, with SANs `localhost`, `127.0.0.1` and
  `<name>.<namespace>.svc`
- a 32-byte random bearer token from `crypto/rand`, base64 encoded

Validity is 24 hours. A development session outliving that should be
restarted.

The client keeps the CA certificate and the token. The server side receives
the leaf, its key, and the token. Because nothing touches the user's
filesystem, a `SIGKILL` leaves no credential material behind.

### Why those SANs

The client dials `127.0.0.1:<port>` through the port-forward. A certificate
naming `127.0.0.1` verifies under ordinary hostname checking, so no
`--server-host-override` is needed. That flag stays for bring-your-own-cert
users and stops being load-bearing.

## Delivery to the pod

### `expose`, with a Secret

A Secret named after the deployment, created **before** the Deployment,
holding `tls.crt`, `tls.key` and `token`. It is mounted at `/ktunnel/creds`.

The container receives:

- `--cert /ktunnel/creds/tls.crt` and `--key /ktunnel/creds/tls.key` as
  **two separate arguments each**. Today `newContainer` appends
  `fmt.Sprintf("--cert %s", cert)`, one argv entry containing a space, which
  no flag parser splits. The bug is fixed on the same line that first starts
  using this path.
- the token via `valueFrom.secretKeyRef`, never as an argument. Arguments are
  visible in `kubectl get pod -o yaml` to anyone with `get pods`.

### `expose`, fallback without a Secret

When `secrets: create` is forbidden: no Secret, no TLS, and the token as a
literal env value in the pod spec. The pre-flight plan introduced in v2.3
states this on a line of its own, naming the namespace and the missing verb.

The trade is deliberate. A token in a pod spec is readable by anyone with
`get pods` in that namespace — a far smaller set than "anything that can
reach the Service", so it is a strict improvement on today. A private key in
a pod spec would be the whole channel, which is why the fallback drops TLS
rather than carrying a key.

### `inject`

Token via env var, no volume, no TLS. Eject stays what it is today: remove
one container. A partial eject that leaves a volume and volumeMount behind in
someone else's Deployment is worse than the encryption it would buy.
`docs/security.md` states this and why.

## Enforcement

Two interceptors. **No proto change**, so no `make proto` and no wire-format
break.

**Server:** a `grpc.StreamInterceptor` reads `authorization` from the
stream's incoming metadata and compares it to the configured token with
`subtle.ConstantTimeCompare`, returning `codes.Unauthenticated` on a
mismatch. A server configured without a token keeps today's open behaviour,
which is what `--insecure` and standalone `ktunnel server` rely on.

The interceptor runs before `InitTunnel`, so a rejected caller never reaches
the code that binds a listener on a tunnelled port. An unauthenticated
attacker cannot even cause a port to open.

**Client:** `grpc.WithPerRPCCredentials` supplies the same header. Its
`RequireTransportSecurity()` returns false, so the token still works on the
fallback's plaintext path.

## Version skew

When the run mounted a Secret it expects TLS. If the handshake then fails,
the server image is older than the local binary.

This does not abort. It logs one line naming the image, saying the tunnel is
unencrypted and unauthenticated, and pointing at `--image`; then it retries
in plaintext. The retry is once per supervisor attempt, not per reconnect, so
a stale image does not spam the log on every backoff.

## Teardown

`ResourceTracker` grows `secrets []string` beside `deployments` and
`services`, with `AddSecret`/`RemoveSecret` and deletion inside the same
30-second bounded sweep.

Cleanup order is Deployment, then Service, then Secret. Deleting credentials
out from under a running pod produces a confusing crash-loop on the way out.

`--reuse` keeps its v2.3 rule unchanged: a Secret this run created is
deleted, one it adopted is left.

## Flag surface

| Flag | Before | After |
|---|---|---|
| `--tls` (expose, inject) | hard error | accepted, no-op, deprecated in help |
| `--insecure` | — | new; turns off both TLS and auth |
| `--cert` / `--key` | hard error | bring your own server credentials |
| `--ca-file` | hard error | bring your own CA for verification |
| `--tls` (server, client) | works | unchanged |

Supplying `--cert`/`--key` skips `creds.Generate()` and builds the Secret
from the given files. `rejectInClusterTLS` and its long error message are
deleted.

## Remaining v2.4 items

- **Least-privilege RBAC** (`docs/rbac.yaml`): ServiceAccount, Role and
  RoleBinding generated from the verb table already in `docs/security.md`,
  plus the new `secrets: get, create, delete`. The forbidden-error message
  added in v2.3 points at it.
- **Ingress annotation for TLS backends** (#69): emitted so a TLS-terminating
  ingress talks to the now-TLS server.

## Testing

- `pkg/creds`: SANs present, leaf verifies against its CA, token length and
  uniqueness across calls.
- Interceptor: accept, wrong token, no token configured.
- `pkg/k8s` manifests: Secret shape; volume and volumeMount present; `--cert`
  and `--key` are four argv entries, not two; the token is a `secretKeyRef`
  and never a literal when a Secret exists.
- Fallback: no-Secret path yields a literal env var, no TLS args, and no
  volume.
- End-to-end: client and server over TLS with a generated bundle, covering
  the two halves meeting.

## Out of scope

- Rotating credentials mid-session. A run is short and generates fresh
  material each time.
- Client certificates / mTLS. The bearer token authenticates the client; a
  second mechanism for the same property is not worth the flags.
- Authorizing *which* client may attach beyond holding the token.
